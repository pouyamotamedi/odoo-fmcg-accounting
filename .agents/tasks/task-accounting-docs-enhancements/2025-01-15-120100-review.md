# Accounting page rewrite with dynamic chart-of-accounts and CRUD management (v2)

This change delivers an accounting documents page with Jalali date-range and partner filters driving server-side queries, dynamic account selection from the chart of accounts, and payment/receipt creation via `account.payment`. A Chart of Accounts management page provides CRUD and a bulk Persian rename utility. The Sidebar gains new nav entries and pulls the company name from Odoo via a persisted Zustand store.

The v1 review raised 8 issues. Issues 1-5 and 7 were addressed in this revision: the filter predicates now differentiate inbound/outbound by narration keywords, the double `fetchEntries` on mount is removed, no-partner submissions auto-assign "مشتری عمومی", the rename loop collects per-iteration errors, quick-action cards notify when no matching account exists, and the Jalali range is computed once via `useState` initializer. Issues 6 (N+1 in `getBankCashBalances`) and 8 (service worker error swallowing) were correctly identified as pre-existing and left out of scope.

**Watch for:**
1. The inbound/outbound filter relies on the memo containing "دریافت"/"پرداخت" keywords — entries created by other modules or directly in Odoo (without those keywords in narration/ref) will be miscategorized and hidden (likely).
2. Warning notifications from quick-action cards display in a green badge, visually indistinguishable from success messages (confirmed).
3. `fetchEntries` is called inside a `useEffect` whose dependency array omits the function itself — functionally correct today but fragile if the function's closure dependencies change (possible).

**Verdict**: APPROVED

## High-level view

The filter predicates now differentiate inbound from outbound by matching Persian keywords in narration/ref. This works for entries created through this UI (which stamps "پرداخت به" / "دریافت از" into the memo), but will silently exclude journal entries created elsewhere in Odoo that lack those keywords.

The notification system uses a single `msg` state with a hardcoded green badge. Warning messages from quick-action cards appear visually identical to success confirmations.

## Filter predicates rely on memo keywords

The fix differentiates inbound and outbound by checking narration/ref for "دریافت" vs. "پرداخت":

```typescript
if (filterType === 'in') {
  if (e.move_type !== 'entry') return false;
  const text = `${e.narration || ''} ${e.ref || ''}`;
  if (!text.includes('دریافت') && !text.includes('inbound')) return false;
}
if (filterType === 'out') {
  if (e.move_type !== 'entry') return false;
  const text = `${e.narration || ''} ${e.ref || ''}`;
  if (!text.includes('پرداخت') && !text.includes('outbound')) return false;
}
```

Entries created directly in Odoo (e.g., through the backend's payment register wizard) will have `ref` set to something like "BNK1/2025/0001" without those Persian keywords. Those entries will fall through both filters and only appear under "همه اسناد". For an FMCG shop where most entries flow through this UI, this is acceptable, but it should be documented or revisited if backend-originated entries become common.

## Notification color mismatch

`handleQuickAction` produces warning messages:

```typescript
setMsg(`⚠️ حساب مرتبط با "${keyword}" یافت نشد. ابتدا حساب‌ها را بررسی کنید.`);
```

The render path applies a single style:

```tsx
{msg && <span className="text-sm bg-green-500 text-white px-3 py-1.5 rounded-lg">{msg}</span>}
```

A green badge with a warning emoji creates cognitive dissonance. A simple conditional — `msg.startsWith('⚠️') ? 'bg-amber-500' : 'bg-green-500'` — would resolve this.
