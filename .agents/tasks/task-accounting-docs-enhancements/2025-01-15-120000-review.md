# Accounting page rewrite with dynamic chart-of-accounts and CRUD management

This change replaces the hardcoded accounting document workflow with a dynamic one backed by Odoo's chart of accounts. The accounting page (`/admin/accounting`) gains Jalali date range and partner filters that drive server-side queries, a dynamic accounts dropdown replacing the old `DocReason` enum, and quick-action cards that match accounts by keyword. A new Chart of Accounts management page (`/admin/chart-of-accounts`) provides full CRUD plus a one-click Persian rename utility for the default Odoo accounts. The Sidebar gains new navigation entries for treasury, accounting, and chart-of-accounts. Alongside this, a substantial amount of supporting infrastructure landed: offline POS queue with IndexedDB, service worker, PAX terminal integration, partner balance ledger, and full implementations of most admin pages.

**Watch for:**
1. The client-side `filterType` logic in the accounting page is broken: `'in'` and `'out'` filters both apply the same predicate (`e.move_type !== 'entry'`), making them functionally identical — they can never distinguish inbound from outbound (confirmed).
2. Double `fetchEntries()` on mount: two `useEffect` hooks both call `fetchEntries()` on the initial render, causing a redundant network round-trip (confirmed).
3. The `handleRenameAccounts` loop issues sequential awaited `searchRead` + `updateAccount` calls (up to 18 requests serially) with no batching and no rollback on partial failure (confirmed).
4. `account.payment` without `partner_id` when the user leaves the partner dropdown empty — Odoo 18 requires a partner on payments; this will 400 at the server (likely).

## High-level view

The accounting page fetches `account.move` entries within a Jalali date range, applying date and partner filters server-side via Odoo domain tuples, with type and text search applied client-side afterward. The client-side type filter has a logic error that makes the "Receipts" and "Payments" buttons indistinguishable — both check `move_type !== 'entry'`.

Payment creation uses `account.payment` with `action_post` and `destination_account_id` to route funds to the chosen chart-of-accounts entry. When no partner is selected, the code omits `partner_id` entirely, but Odoo's payment model mandates a partner for both inbound and outbound types, which will produce a server error for "anonymous" expense entries.

The Chart of Accounts page is a CRUD surface with a rename utility that iterates 9 code-to-name mappings sequentially. A failure mid-loop leaves some accounts renamed and others untouched with no indication of which ones failed.

The `getBankCashBalances` function performs an N+1 query pattern: after fetching all bank/cash journals, it loops through each journal issuing a `searchRead` against `account.move.line`. For the typical 2-4 journal case latency is manageable, but the pattern won't scale.

## Broken filterType predicates on the accounting list

The client-side filter for receipts vs. payments applies the same logic:

```typescript
if (filterType === 'in' && e.move_type !== 'entry') return false;
if (filterType === 'out' && e.move_type !== 'entry') return false;
```

Both conditions exclude anything that isn't `move_type === 'entry'`. Entries created via `account.payment` all land with `move_type: 'entry'`, so without inspecting the payment direction (via the related `account.payment` record's `payment_type` field, or the debit/credit pattern on the journal's line), these two filter tabs will always show identical results.

## Double effect firing fetchEntries on mount

```typescript
useEffect(() => { fetchEntries(); fetchJournals(); fetchPartners(); fetchAccounts(); }, []);
useEffect(() => { fetchEntries(); }, [dateFrom, dateTo, filterPartnerId]);
```

On initial render, `dateFrom`, `dateTo`, and `filterPartnerId` all have values (defaults), so both effects fire. Two concurrent `searchRead` calls to `account.move` with identical domains result.

## Payment creation without partner_id

When the user leaves the partner dropdown empty (labeled "optional"), the code omits `partner_id`:

```typescript
if (form.partner_id) {
  paymentData.partner_id = form.partner_id;
}
```

Odoo 18's `account.payment` raises a `ValidationError` if `partner_id` is falsy. Any expense entry without a named partner will fail at submission. The POS page already handles this pattern by auto-creating "مشتری عمومی" — the same approach should be applied here, or the field should be marked required.

## Rename accounts atomicity

```typescript
for (const mapping of RENAME_MAPPINGS) {
  const results = await searchRead(...);
  if (results && results.length > 0) {
    await updateAccount(results[0].id, { name: mapping.persianName });
    successCount++;
  }
}
```

If the third `updateAccount` throws, the first two are committed and the remaining six are skipped. The user sees "۲ حساب با موفقیت تغییر نام یافت" with no indication of what failed. Wrapping each iteration in try/catch and accumulating failures would provide actionable feedback.

## getCurrentJalaliMonthRange recomputed per render

`defaultRange` is computed in the component body on every render, though `useState` only consumes the initial value. Moving it to a `useState` initializer (`useState(() => getCurrentJalaliMonthRange())`) eliminates redundant `jalaali` calculations.

## Service worker registration failure path

```typescript
navigator.serviceWorker.register('/sw.js').catch(() => {});
```

Registration failures (HTTPS requirement, scope mismatch, syntax error in sw.js) are silently swallowed. The app continues showing the online badge while offline capability is absent. Logging the error at minimum, or setting a flag that disables the "offline ready" UI, would prevent user confusion.
